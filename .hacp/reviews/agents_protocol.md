# Cross-agent protocol review

## Findings

1. **High — deployment and cutover can race, putting an unverified build into production.** References: `agents/translator_agent.py:552-557`, `agents/translator_agent.py:608-619`, `agents/cutover_agent.py:318-356`. Scenario: the human sends another decision command while approving verified build R2. The translator reads no active cutover, then pauses before deploying R3. The gate flips to modern, verifies R2 and records the cutover. The translator resumes and deploys R3 without checking the cutover again. Production now serves R3 without parity verification or approval; the subsequent `record-cutover rev=R2` is rejected because R3 is the latest build. Fix: serialize deployment and cutover with a shared lock or durable interlock covering the translator's active-cutover check through deployment, and the gate's revision checks through flip and scorecard commit.

2. **High — failed recovery clears the state that prevents the translator from rewriting production.** References: `agents/cutover_agent.py:377-389`, `agents/cutover_agent.py:419-431`, `agents/translator_agent.py:373-376`. Scenario: a flip to modern succeeds, post-flip verification fails, and the automatic revert fails while the proxy remains on modern. `_abort_cutover` nevertheless sets `cutover = None` when the previous target was legacy and saves that state. The translator then accepts `migrate` or new decisions because `_active_cutover()` sees no modern cutover, replacing the live module. Manual rollback also clears the cutover before handling failed verification. Fix: retain a blocking pending/unknown state until legacy routing is positively verified, and make translator deployment refuse that state or an unreachable proxy.

3. **High — replaying an old approval after rollback flips production again.** References: `agents/cutover_agent.py:313-328`, `agents/cutover_agent.py:336-356`, `agents/cutover_agent.py:427-428`. Scenario: approval message A flips R2 to modern; rollback message B restores legacy and clears the active cutover. Redelivery of A passes the unchanged benchmark/parity checks. The duplicate guard only recognizes an already-active matching modern cutover, so the gate flips back to modern using the old approval. A replayed rollback can similarly undo a later approval. Fix: persist processed governance message IDs and their outcomes independently of the active cutover, and suppress routing mutations for previously applied IDs.

4. **High — the translator can seal a gate-fabricated human approval.** References: `agents/translator_agent.py:673-681`, `agents/translator_agent.py:739-759`. Scenario: with genuine approved parity and benchmark evidence for the current build, a compromised cutover gate writes a cutover naming human `user` and uses the ID of that human's `status — do NOT approve-cutover` message as approval evidence. `_check_approval()` accepts the substring even though `parse_cutover()` would classify the message as `status`. Missing approval IDs, unavailable messages and history-read failures also return no blocking problem, so sealing proceeds without verified approval. Fix: require an actual human approval message addressed to the gate, validate it with `parse_cutover()` and require `approve-cutover`; leave sealing pending when approval evidence cannot be verified.

5. **Medium — the fuzzer can approve a historical build that the translator will refuse to seal.** References: `agents/fuzzer_agent.py:402-409`, `agents/fuzzer_agent.py:429-433`, `agents/cutover_agent.py:263-264`, `agents/cutover_agent.py:317-319`, `agents/translator_agent.py:648-652`. Scenario: the ledger records equivalent builds R1 and R2, with R2 latest, but a stale service restart serves R1. A human requests verification of R1. The fuzzer accepts any recorded build, approves R1, and hands it to the gate, which benchmarks and flips it after approval. The translator then rejects `record-cutover rev=R1` because its latest build is R2. The fuzzer also allows a campaign without any ledger, permitting another unsealable cutover. Fix: require a matching translator ledger with a nonempty build list and require the requested revision to equal its latest build before allowing promotion.

6. **Medium — committed stages suppress the redelivery needed to recover a lost handoff.** References: `agents/fuzzer_agent.py:271-274`, `agents/fuzzer_agent.py:322-342`, `agents/translator_agent.py:455-457`, `agents/translator_agent.py:504-511`, `agents/translator_agent.py:547-551`, `agents/translator_agent.py:619-631`. Scenario: the fuzzer commits an approved campaign, then its campaign post or benchmark handoff fails. Redelivery of the triggering message hits the “already handled” return and never retries the benchmark handoff, leaving the loop stalled. Translator migration and decision commits have the same gap before their outgoing fuzzer handoffs. Fix: persist pending outgoing notifications and handoffs alongside the stage result, retry them after failures or restart, and let duplicate commands resume delivery without repeating deployment or campaign work.
